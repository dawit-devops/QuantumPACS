# ADR-020: Observability Stack — Structured Logs + OpenTelemetry + Prometheus

## Status
Accepted

## Date
2026-07-25

## Context

QuantumPACS v2.0 observability is minimal:

- **Logging**: Plain-text `logging.Formatter` with hardcoded `INFO` level. No structured fields (JSON), no correlation IDs, no tenant context. Log aggregation systems (Loki, ELK, Splunk) cannot parse effectively.
- **Metrics**: In-memory Python dict in `telemetry.py` exposed at `/api/metrics` as JSON. Not Prometheus exposition format. No histograms, no percentiles.
- **Tracing**: None. No way to trace a request from HTTP handler through database queries, Redis operations, and DICOM file I/O.

Production-grade observability requires:
1. **Structured logging** with JSON output, correlation IDs, and tenant context for log aggregation
2. **Request-level tracing** with OpenTelemetry to diagnose latency across services and async boundaries
3. **Standard metrics** in Prometheus exposition format for alerting and dashboarding
4. **Component health checks** for automated recovery and load balancer integration

## Decision

### 1. Structured Logging

Replace the v2 plain-text formatter with a **JSON formatter** in `log.py`.

**Log record schema:**
```json
{
  "timestamp": "2026-07-25T12:00:00.000Z",
  "level": "ERROR",
  "logger": "backend.api.files",
  "message": "File not found",
  "request_id": "req_abc123",
  "tenant": "hospital_a",
  "user_id": "user_42",
  "trace_id": "0xdeadbeef...",
  "span_id": "0xcafebabe...",
  "file_id": "file_99",
  "error": {
    "type": "FileNotFoundError",
    "message": "File not found in storage",
    "stack": "Traceback (most recent call last): ..."
  }
}
```

**Fields:**
- `timestamp` — ISO 8601 with timezone
- `level`, `logger`, `message` — standard logging fields
- `request_id` — UUID generated by middleware, propagated to all logs in the request lifecycle
- `tenant` — resolved from request context (empty for global operations)
- `user_id` — from authenticated user (empty for unauthenticated)
- `trace_id`, `span_id` — from OpenTelemetry span context
- Domain-specific fields (`file_id`, `study_uid`, `dicom_status`) — added by domain loggers
- `error` — structured error object (type, message, stack) only present on error-level logs

**Implementation:**
- Custom `logging.Formatter` that outputs JSON
- `request_id` injected via middleware using `contextvars` (already partially scaffolded in v2)
- `tenant` and `user_id` injected via middleware after auth
- `LOG_LEVEL` env var (already added in hardening Sprint 0)

### 2. OpenTelemetry Tracing

Adopt OpenTelemetry for distributed tracing. All services (monolith + ingestion service) export spans to a configurable OTLP endpoint.

**Instrumentation scope:**

| Component | Spans | Attributes |
|-----------|-------|------------|
| HTTP middleware | Per-request | `http.method`, `http.route`, `http.status_code`, `http.url` |
| Database (asyncpg) | Per-query | `db.statement` (first 200 chars), `db.system` |
| Redis Streams | Per-publish, per-consume | `messaging.destination`, `messaging.message_id` |
| Storage backends | Per-read/write/delete | `storage.backend` (local/s3/b2), `storage.operation` |
| DICOM listener | Per-C-STORE | `dicom.study_uid`, `dicom.instance_count`, `dicom.transfer_size` |
| DICOMweb endpoints | Per-request | `dicomweb.resource` (study/series/instance), `dicomweb.service` (QIDO/STOW/WADO) |
| HL7 MLLP listener | Per-message | `hl7.message_type` (ADT/ORM), `hl7.event` (A01/A08/A03) |

**Trace propagation:**
- W3C Trace Context (`traceparent` header) propagated across:
  - HTTP request → internal service calls
  - Redis Streams producer → consumer (via message attributes)
  - asyncpg queries (via connection attributes)
  - Outbound HTTP calls (to S3, B2, external APIs)

**Configuration:**
- `OTEL_EXPORTER_OTLP_ENDPOINT` — OTLP gRPC endpoint (default: `http://localhost:4317`)
- `OTEL_SERVICE_NAME` — `quantumpacs-backend` / `quantumpacs-ingestion`
- `OTEL_SAMPLER` — `parentbased_traceidratio` with configurable rate (default 0.1 for production, 1.0 for staging)

### 3. Prometheus Metrics

Replace the v2 JSON metrics with `prometheus_client` standard metrics at `/api/v2/metrics`.

**Metric catalog:**

| Metric Name | Type | Labels | Source |
|-------------|------|--------|--------|
| `http_requests_total` | Counter | `method`, `path`, `status_code`, `tenant` | HTTP middleware |
| `http_request_duration_seconds` | Histogram | `method`, `path` | HTTP middleware |
| `http_requests_in_progress` | Gauge | `method`, `path` | HTTP middleware |
| `db_connections_available` | Gauge | `tenant` | Connection pool |
| `db_connections_in_use` | Gauge | `tenant` | Connection pool |
| `db_query_duration_seconds` | Histogram | `operation` (SELECT/INSERT/UPDATE/DELETE) | asyncpg instrumentation |
| `redis_stream_lag_seconds` | Gauge | `stream`, `consumer_group` | Consumer group monitor |
| `redis_stream_messages_total` | Counter | `stream`, `action` (publish/consume/ack) | Stream producer/consumer |
| `dicom_cstore_throughput_bytes` | Counter | `study_uid` | DICOM listener |
| `dicom_cstore_duration_seconds` | Histogram | — | DICOM listener |
| `dicom_cstore_concurrent` | Gauge | — | DICOM listener |
| `dicomweb_requests_total` | Counter | `service` (QIDO/STOW/WADO), `resource` | DICOMweb endpoints |
| `storage_operation_duration_seconds` | Histogram | `backend` (local/s3/b2), `operation` | Storage backends |
| `storage_used_bytes` | Gauge | `backend`, `tenant` | Periodic aggregation |
| `hl7_messages_received_total` | Counter | `message_type`, `event_type` | HL7 listener |
| `fhir_requests_total` | Counter | `resource_type`, `operation` | FHIR endpoints |

### 4. Component Health Checks

`GET /api/v2/health` returns a JSON object with per-component status:

```json
{
  "status": "ok",
  "uptime_seconds": 86400,
  "components": {
    "database": { "status": "ok", "latency_ms": 2 },
    "redis": { "status": "ok", "latency_ms": 1 },
    "storage_master": { "status": "ok", "backend": "local" },
    "storage_replicas": { "status": "degraded", "backends": ["s3", "b2"], "message": "b2 sync lag: 30s" },
    "elasticsearch": { "status": "degraded", "message": "ES unavailable, search fallback active" },
    "dicom_listener": { "status": "ok", "port": 11112, "uptime_seconds": 86400 },
    "ingestion_service": { "status": "ok", "stream_lag": 0 }
  }
}
```

Each component probe:
- **Critical**: Component failure degrades core functionality (database, redis)
- **Non-critical**: Component failure degrades specific features (elasticsearch, storage replicas)

## Consequences

### Positive

- **Production debugging**: Structured logs + trace ID correlation enable debugging across the monolith, ingestion service, and async boundaries.
- **Alerting**: Prometheus metrics enable alerting on latency spikes, error rates, consumer lag, and storage capacity.
- **Performance visibility**: p50/p95/p99 latency histograms give continuous performance insight without load testing.
- **Health-based routing**: Component health checks enable load balancers to route around degraded instances.

### Negative

- **OTLP collector dependency**: Traces require an OTLP collector (Grafana Tempo, Jaeger, or similar). Without it, spans are dropped. Mitigation: console exporter in development, configurable OTLP endpoint in production.
- **Log volume increase**: JSON logs are ~3× larger than plain-text (field names in every record). At 100 req/s, this adds ~1 GB/day. Acceptable for modern log aggregation systems.
- **Metric cardinality**: Per-tenant labels on metrics increase cardinality with tenant count. At 50 tenants, this is manageable. Mitigation: aggregate tenant metrics into `tenant` label, not per-tenant metric.

# IAM Audit Report — QuantumPACS

## Scope
Application identity & access layer: JWT identity (api/tokens.py, api/auth.py, api/users.py), authorization model (api/permissions.py, api/rbac.py, api/roles.py), tenant isolation (api/tenant_middleware.py, db/conn.py, db/tenants.py, api/tenants.py), service identities (DICOM AE, MLLP/HL7, FHIR, ES, ingestion worker), audit trail & metering (db/audit_log.py, db/metering.py), operational access (scripts/*, docker-compose.yaml, config), and frontend auth flows (AuthContext, TenantSelector, client.ts).
## Date
2026-08-06 · Mode: **Audit** (read-only, no files modified) · Method: 3 parallel read-only reviewers with cross-validation; all file:line claims verified against source.

### Executive Summary

The identity *data plane* is solid: per-tenant PostgreSQL databases with slug-keyed pools and ContextVar request scoping give real DB-level separation; the signed JWT tenant claim takes priority over the `X-Tenant-ID` header; algorithm pinning (HS256 only), 600k-iteration PBKDF2 with constant-time compare, token versioning, JTI blocklist with rotation, HttpOnly/SameSite cookies, CSP/HSTS, and explicit public-path allowlists are all in place.

The *control plane* is not: four critical paths allow privilege escalation to platform super-admin or bypass revocation entirely, and — most relevant to the multi-tenancy work just shipped — the new `TENANT_*` permission family is **platform-wide, never tenant-scoped**: a `tenant_admin` can read, suspend, re-point, or decommission *other* tenants, and read platform-wide usage/health. A `tenant_admin` can also mint an API key with `permissions: ["*"]` (super-admin-equivalent, platform-wide) because API-key permission sets are stored verbatim with no subset check and the RBAC core honors the legacy `'*'` wildcard. Default/committed credentials (`pa55w0rd` superadmin, a repo-committed dev secret) defeat `assert_production_secret()`, and two clinical ingest surfaces (MLLP — with SQL injection — and the DICOM AE) run unauthenticated by default.

Top 3 risks: (1) tenant_admin → platform super-admin via API-key `['*']` or `TENANT_*` handler scope; (2) OAuth refresh grant + WebSocket path bypass token revocation/status checks; (3) default/committed credentials passing the production startup guard.

### Per-finding detail (key remediation)

**C1 — API-key `['*']` minting (shadow admin).** `backend/api/api_keys.py:14,45` stores `body.permissions` verbatim; `backend/db/api_keys.py:62` persists; `backend/api/rbac.py:29-31` treats `'*'` as full grant; `backend/api/auth.py:186-192` loads them into the service principal. Remediation: validate requested ⊆ creator's own grants; reject `'*'`; per-key tenant scoping; return key material once. *(Note: this is the classic "shadow admin" finding — a tenant_admin is one HTTP call away from platform super-admin.)*

**C2 — OAuth refresh grant.** `backend/api/oauth.py:310-322`: `grant_type=refresh_token` → `verify_token(refresh_token)` (no type check, `tokens.py:107-114` verifies only `exp`) → mints new pair with `admin` claim. Remediation: `verify_refresh_token`, blocklist + `token_version` + status checks, rotate consumed token, re-read role/tenant from DB.

**C3 — MLLP SQL injection.** `backend/services/ingestion/hl7_server.py:284-289`: `meta_updates += f', "tenant_id": "{facility}"'` with MSH-4 attacker-controlled. Remediation: `jsonb_build_object(...)` with bound parameters; charset validation; TLS + IP allowlist required in production.

**C4 — Credentials defeating the guard.** `backend/config.py:8-9` (`pa55w0rd` superadmin default, seeded at `lifecycle.py:254`), `scripts/dev.sh:43` / `scripts/setup_dev.sh:106` commit the dev secret; `config.py:95-99` deny-list misses both. Remediation: generate secrets per install; add known values to the deny-list; require `SUPERADMIN_PASS`.

**H5/H1/M2/M17/L8 — our multi-tenancy code (fix within this branch):** scope `TENANT_*` handler access to the caller's own tenant slug (super_admin exempt) — `api/tenants.py`, `api/metering.py`, `api/tenant_health.py`; require `METERING_READ` (or SYSTEM_ADMIN) for `/usage` + `/tenants/health`; gate `X-Tenant-ID` for anonymous requests (`api/tenant_middleware.py:48-61`); keep `db_password` out of handler-visible dicts (`api/tenants.py:146-153`, `api/tenant_health.py:89`); close pools by slug (`db/tenants.py:146-147`).

**H6 — role escalation at user creation.** `backend/api/schemas/users.py` exposes `admin: bool` ("Grant superadmin privileges"); `api/users.py:174-222` lets any USER_WRITE holder set it and assign any role. Remediation: only super_admin may set `admin=True`; cap assignable roles to caller's subset; never return plaintext passwords; bump `token_version` on reset.

### Strengths (verified)

Per-tenant DB isolation + slug-keyed pools + ContextVar scoping; JWT claim priority over header with `can_access_tenant` gate; HS256 algorithm pinning; PBKDF2 600k + constant-time compare; token versioning + JTI blocklist with rotation on refresh; HttpOnly/SameSite=Strict/Secure cookies, CSRF custom-header + CSP/HSTS/X-Frame-Options/nosniff, TrustedHost; explicit narrow public-path allowlist; PKCE S256 with single-use state; secrets encrypted at rest (Fernet); tenant status gates (suspended/quarantined→403, decommissioned→404); random per-tenant admin passwords; per-tenant pools LRU-capped; 1240 backend + 413 frontend tests green including tenant isolation routing tests.
